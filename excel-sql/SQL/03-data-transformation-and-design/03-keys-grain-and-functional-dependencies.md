# درس ۳ — کلیدها، Grain و وابستگی تابعی

در تحلیل داده، فقط دانستن نام ستون‌ها کافی نیست. باید بدانیم هر ردیف دقیقاً نماینده چیست، کدام ستون‌ها یک رکورد را یکتا می‌کنند و چه رابطه‌ای میان ویژگی‌ها وجود دارد.

این مفاهیم در طراحی دیتابیس مطرح‌اند، اما برای تحلیلگر داده نیز اهمیت عملی دارند؛ به‌ویژه هنگام تشخیص Duplicate، اتصال جدول‌ها و جلوگیری از شمارش اشتباه.

## ۱. Grain چیست؟

**Grain** یا سطح جزئیات جدول مشخص می‌کند هر ردیف دقیقاً نماینده چه چیزی است.

در دیتابیس تمرینی:

| جدول | Grain هر ردیف |
|---|---|
| customers | یک مشتری |
| products | یک محصول |
| orders | یک سفارش |
| order_items | یک قلم کالا در یک سفارش |

این تعریف مهم است. برای مثال یک سفارش ممکن است سه قلم کالا داشته باشد؛ پس بعد از اتصال Orders به Order Items، سه ردیف برای آن سفارش خواهیم دید.

اگر پس از این JOIN تعداد سفارش‌ها را با COUNT(*) بشماریم، تعداد اقلام را به‌جای تعداد سفارش‌ها گزارش کرده‌ایم. باید از `COUNT(DISTINCT order_id)` استفاده کنیم.

## ۲. Super Key چیست؟

ابرکلید (Super Key) هر مجموعه‌ای از ستون‌هاست که بتواند هر ردیف را از سایر ردیف‌ها متمایز کند.

در جدول مشتریان، اگر `customer_id` یکتا باشد، خود آن یک Super Key است. ترکیب `customer_id` و `email` نیز یکتایی را حفظ می‌کند؛ اما ستون اضافه‌ای دارد که برای تشخیص رکورد ضروری نیست.

## ۳. Candidate Key چیست؟

کلید کاندید (Candidate Key) یک Super Key کمینه است؛ یعنی اگر یکی از ستون‌های آن را حذف کنیم، دیگر یکتایی تضمین نمی‌شود.

برای جدول customers، اگر هم `customer_id` و هم `email` در کل جدول یکتا باشند، هر دو می‌توانند Candidate Key باشند. طراح دیتابیس یکی از آن‌ها را به‌عنوان Primary Key انتخاب می‌کند.

| مفهوم | توضیح |
|---|---|
| Super Key | هر ترکیب ستونی که ردیف را یکتا مشخص کند |
| Candidate Key | Super Key کمینه |
| Primary Key | Candidate Key انتخاب‌شده به‌عنوان کلید اصلی |

در عمل، برای جدول‌های اصلی از یک شناسه پایدار مانند customer_id استفاده می‌کنیم و با UNIQUE نیز می‌توانیم یکتایی ایمیل را کنترل کنیم.

## ۴. وابستگی تابعی (Functional Dependency)

وابستگی تابعی رابطه‌ای میان ستون‌هاست. اگر مقدار ستون A مقدار ستون B را به‌صورت یکتا تعیین کند، می‌نویسیم:

`A → B`

برای مثال، در جدول مشتریان انتظار داریم:

`customer_id → full_name, email, city, signup_date`

یعنی با دانستن شناسه مشتری، ویژگی‌های ثبت‌شده همان مشتری مشخص می‌شوند.

در جدول محصولات:

`product_id → product_name, category, unit_price`

این رابطه باید با قواعد کسب‌وکار و Constraintهای دیتابیس سازگار باشد؛ صرف مشاهده چند ردیف نمونه برای اثبات آن کافی نیست.

## ۵. وابستگی کامل و وابستگی باواسطه؛ فقط به اندازه نیاز تحلیلگر

گاهی برای تعیین یک ویژگی به ترکیب چند ستون نیاز داریم. فرض کنید یک جدول نتیجه آزمون شامل `student_id` و `course_id` باشد. اگر هر دانشجو در هر درس فقط یک نمره نهایی داشته باشد، ترکیب این دو ستون می‌تواند نمره را تعیین کند:

`(student_id, course_id) → final_score`

اگر هیچ‌یک از دو ستون به‌تنهایی نمره را تعیین نکند، وابستگی به کل ترکیب نیاز دارد.

وابستگی باواسطه زمانی رخ می‌دهد که A مقدار B را تعیین کند و B نیز مقدار C را تعیین کند؛ در نتیجه A از طریق B، مقدار C را مشخص می‌کند:

`A → B` و `B → C`

مثلاً در جدول سفارش فرض کنیم:
- `order_id → customer_id`
- `customer_id → city`

بنابراین شهر مشتری از طریق شناسه مشتری به سفارش وابسته است. ذخیره کردن شهر مشتری در تمام سفارش‌ها می‌تواند تکرار داده ایجاد کند؛ مگر اینکه عمداً بخواهیم Snapshot شهر در زمان سفارش را نگهداری کنیم.

## ۶. چرا این مفاهیم برای تحلیل داده مهم‌اند؟

### تشخیص Duplicate واقعی

وجود دو ردیف با یک customer_id در جدول مشتریان احتمالاً مشکل است؛ اما تکرار customer_id در جدول orders طبیعی است، چون هر مشتری می‌تواند چند سفارش داشته باشد.

پس قبل از حذف Duplicate باید Grain جدول را بدانیم.

### جلوگیری از خطای JOIN

اگر جدول سمت راست چند ردیف برای هر کلید داشته باشد، اتصال می‌تواند تعداد ردیف‌ها را افزایش دهد. این رفتار همیشه خطا نیست؛ اما روی SUM و COUNT اثر می‌گذارد.

### انتخاب شاخص درست

برای محاسبه تعداد مشتری، `COUNT(DISTINCT customer_id)` ممکن است مناسب باشد؛ اما برای تعداد اقلام فروخته‌شده، SUM(quantity) شاخص درست‌تری است. نوع سؤال باید با Grain و ستون محاسبه‌شونده هماهنگ باشد.

## ۷. یک بررسی عملی برای یکتایی

برای بررسی تکراری بودن ایمیل‌ها:

```sql
SELECT
    email,
    COUNT(*) AS occurrences
FROM customers
GROUP BY email
HAVING COUNT(*) > 1;
```

برای بررسی اینکه هر سفارش چند قلم دارد:

```sql
SELECT
    order_id,
    COUNT(*) AS item_rows
FROM order_items
GROUP BY order_id
ORDER BY item_rows DESC;
```

این Query دوم به ما کمک می‌کند Grain جدول order_items را بهتر درک کنیم و هنگام JOIN از خطای شمارش جلوگیری کنیم.

## تمرین

1. Grain هر چهار جدول دیتابیس تمرینی را با یک جمله تعریف کنید.
2. مشخص کنید کدام ستون در هر جدول Primary Key است.
3. بررسی کنید آیا در جدول customers ایمیل تکراری وجود دارد یا خیر.
4. توضیح دهید چرا customer_id در جدول orders می‌تواند تکرار شود.
5. یک مثال از وابستگی تابعی در جدول products بنویسید.

## جمع‌بندی

- Grain می‌گوید هر ردیف چه چیزی را نمایش می‌دهد.
- Super Key هر ترکیب یکتاساز است؛ Candidate Key نسخه کمینه آن است.
- Primary Key یکی از Candidate Keyهاست که انتخاب شده است.
- Functional Dependency نشان می‌دهد یک ویژگی کدام ویژگی دیگر را تعیین می‌کند.
- شناخت این مفاهیم، دقت JOIN، COUNT، SUM و کنترل Duplicate را بهبود می‌دهد.
